## 2026-09-05 UI 평가 후속 반영

- 습관 9개는 최소 높이 80px, 간격 8px의 3열 카드로 표시합니다. 360px 미만은 2열로 전환합니다. 순위 숫자와 스크린리더용 순위 텍스트, 1~3개 선택 규칙을 유지합니다.
- 단일 선택 카드는 최소 높이 56px, 내부 여백 12px로 축소합니다. 설명이 있는 카드는 내용에 맞춰 높이가 늘어납니다.

- 기본 정보·일정 화면의 내부 카드 테두리와 중복 제목·설명을 제거합니다. 개인정보 수집 항목·목적·보유 기간·동의 체크는 펼쳐진 상태로 유지합니다.

## 1. 문서 목적

사용자가 전달한 6개 항목(공통, 온도 페이지, 지속 페이지, 습관 페이지, 안내 페이지, 신청 페이지)을 실제 구현 가능한 화면·데이터 단위로 번역합니다. [카드 기반 라이트 리디자인 기획](신청-폼-카드-기반-라이트-리디자인-기획.md)이 "노트 형태 제거"를 다뤘다면, 이 문서는 그 카드 UI 위에서 **질문 난이도, 입력 방식과 페이지 분할**을 다시 조정하는 후속 개편입니다.

이 문서는 기획안이며 아직 구현되지 않았습니다. 실제 반영은 사용자 확정 이후 별도 작업으로 진행합니다.

## 3. 0. 공통 — 직관성·강조색·질문 크기

### 결정

- 질문 제목(`question-heading`) 크기를 모바일 `30~34px`(현재 `26~30px`), 태블릿 이상 `34~38px`(현재 `30~34px`)로 확대합니다.
- 질문 제목 위에 짧은 대문자/한글 캡션 라벨을 추가합니다. 예: `오늘 하루 리듬` 처럼 4~8자의 상태 라벨을 `question-sub-desc` 위에 배치합니다.
- 질문 제목 안에서 핵심 단어 1개에만 강조를 적용합니다. Growth Yellow 전체 텍스트 대신 **Deep Navy 굵은 글자 + 짧은 Growth Yellow 밑줄 마크**를 사용해 대비 기준(WCAG AA)을 지킵니다. 문장 전체를 색칠하지 않습니다.
- 선택 카드 오른쪽의 번호 배지와 습관 카드 왼쪽의 영문 문자 배지는 제거합니다. 장식 정보를 덜어내고 선택 체크와 1~3순위처럼 기능에 필요한 상태만 남깁니다.
- 이 항목은 특정 페이지가 아니라 전체 질문 화면 공통 스타일 변경이므로, 아래 1~5번 항목과 별도로 `App.css`의 공통 타이포그래피·강조 토큰만 수정해 한 번에 적용합니다.

### 영향받지 않는 것

- 카드 기반 라이트 UI의 전체 구조(헤더 → 진행 정보 → 카드 → 하단 행동 영역)는 유지합니다.
- 컬러 토큰 자체는 추가하지 않고 기존 [디자인 토큰](../05-구현-명세/디자인-토큰.md)의 `--color-action`(Growth Yellow), `--color-text-strong`(Deep Navy)만 다른 비중으로 사용합니다.

## 4. 1. 온도 페이지 (현재 Page 02 · `energy_selected`)

> **대체됨 (2026-09-04)**: 이 섹션의 시간대 선택지(아침/점심/저녁/매일 달라요 → 새벽~출퇴근길 7개 버튼)는 [신청폼 활력·피로 상황형 선택 및 기타 입력 기획](신청폼-활력-피로-상황형-선택-기획.md)의 생활 상황형 선택지·기타 입력으로 다시 교체되어 구현됐습니다. 페이지 분할, 진행 막대 5칸 확장과 A안(스키마 미변경) 원칙은 그대로 유지됩니다. 아래 내용은 그 이전 확정 이력으로 남겨둡니다.

### 현재 상태

`힘이 나는 때`, `지치는 때` 두 텍스트 입력 카드가 한 화면에 세로로 배치되어 있고(`src/App.tsx:392-478`), 각 카드 아래 `예시로 입력하기` 칩 4개가 있습니다. 자유 텍스트 입력이 기본값입니다.

### 개편 방향

1. **페이지 분할**: 1개 화면(2입력) → 2개 화면(1선택형씩)으로 나눕니다.
   - Page 02-A: `언제 가장 힘이 나나요?` / 부제 `가장 가까운 시간대를 하나 골라주세요.`
   - Page 02-B: `언제 가장 지치나요?` / 부제 `가장 가까운 시간대를 하나 골라주세요.`
   - 기존 부제 `두 칸에 시간과 상황을 짧게 적어주세요.`는 텍스트 2칸 입력 시절 문구라 폐기합니다.
   - 질문 전체 단계 수가 4 → 5로 늘어나므로 진행 막대(`question-progress`)를 4칸에서 5칸으로 조정합니다.
2. **입력 방식 전환**: 자유 텍스트 우선 → **선택형 버튼 우선**, 텍스트 입력은 `기타`로만 남깁니다. `apply.hyukrecord.com` 03단계의 pill 버튼 + `기타 +` 패턴을 그대로 참고합니다.
3. **'빠른 입력 힌트' 문구 제거**: `quick-example-chips`의 `예시로 입력하기` 라벨과 칩 UI 자체를 없애고, 그 칩들이 곧 선택지 버튼이 됩니다(중복 제거).
4. **선택지 확정 (2026-09-04 사용자 확정)**: 상황을 구체적으로 서술하는 초안 대신, Page 01(오늘의 리듬)과 같은 방식의 단순 시간대 카테고리로 통일합니다. 두 페이지가 같은 선택지 목록을 공유하고 질문 문장만 다릅니다.

   | 선택지 (활력 시간·지치는 시간 공통) |
   | --- |
   | 아침 |
   | 점심 |
   | 저녁 |
   | 매일 달라요 |
   | 기타 (직접 입력) |

   - Page 02-A `언제 가장 힘이 나나요?`와 Page 02-B `언제 가장 지치나요?`에 위 5개 선택지를 동일하게 적용합니다.
   - Page 01의 `dailyRhythm` 선택지(아침에 힘이 나요/낮에 집중이 잘돼요/저녁에 여유가 생겨요/날마다 달라요)와 표현을 맞춰 같은 UI 언어를 씁니다. 다만 `dailyRhythm`은 "하루 전체의 리듬"을, 온도 페이지는 "구체적으로 힘이 나는/지치는 시점"을 묻는 별개 질문이므로 필드 자체를 합치지는 않습니다.
   - `기타`를 선택하면 기존 `clean-time-text-input`이 카드 아래 펼쳐지며, 기존 100자 제한과 검증 로직을 재사용합니다.
   - 기존에 제안했던 `quick-example` 문구(아침 7시 기상 직후, 퇴근길 만원 지하철 등)는 선택지 문구로 쓰지 않고 폐기합니다.

### 데이터 영향 (중요)

이 항목은 **스키마 변경이 필요합니다.** 카드 리디자인과 달리 v3 계약을 유지할 수 없습니다.

- `types.ts`의 `comfortableTime?: string` / `difficultTime?: string`을 유지하되, 선택형 결과를 문자열로 매핑하는 방식(예: 선택한 라벨 텍스트를 그대로 `comfortableTime`에 저장)과 `enum + other` 구조로 나누는 방식 중 하나를 선택해야 합니다.
  - **A안(계약 유지, 권장)**: 버튼 선택 시 해당 라벨 문자열을 `comfortableTime`/`difficultTime`에 그대로 저장합니다. `기타` 선택 시 사용자가 입력한 문자열을 저장합니다. 기존 API·Sheets·테스트 계약(`daylog-life-session-v3`)을 그대로 유지할 수 있습니다.
  - **B안(구조화)**: `comfortableTimeOption: EnergeticMoment`, `comfortableTimeOther?: string` 형태로 분리합니다. 이후 통계·분석은 쉬워지지만 `schemaVersion`을 v4로 올리고 API 검증, Apps Script, Google Sheets 컬럼, `tests/contracts.test.mjs`를 함께 수정해야 합니다.
- 이 문서는 **A안을 기본 권장**으로 제안합니다. 데이터 구조 변경 없이 입력 방식만 바꿀 수 있어 구현 범위가 작고 기존 계약 테스트가 깨지지 않습니다.

- **후속 기획 확정 (2026-09-04, 구현 전)**: 활력·피로 질문을 시간대 대신 생활 상황 중심의 서로 다른 버튼 목록으로 바꾸고, 마지막 `잘 모르겠어요` 대신 `기타`를 선택해 직접 입력받는 방식으로 다시 개편합니다. 이 항목은 위 1·2차 구현 결과보다 최신 기준이며, 세부 문구·상태·검증은 [활력·피로 상황형 선택 및 기타 입력 기획](신청폼-활력-피로-상황형-선택-기획.md)을 따릅니다.
- 신청 퍼널 이벤트는 온도 페이지의 두 번째 화면(지치는 시간)에서만 `energy_selected`를 전송하도록 해 기존 9단계 퍼널 계약을 그대로 유지했습니다. `tests/contracts.test.mjs`의 "client, API and Apps Script share the same nine-stage funnel" 테스트로 확인했습니다.
